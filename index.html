机器：4 张 B200，两颗 Grace

一个 GB200 superchip 是 1 颗 Grace CPU 加 2 颗 B200 GPU。我们用两个 superchip，共 4 张卡。

4 张卡之间任意两两都是 NV18，18 条 NVLink 5，单向 900 GB/s，没有“远端”卡。每颗 Grace 通过 NVLink-C2C（900 GB/s）连着自己的两张卡。已核实nvidia-smi topo -m

decode 时决定速度的是另一条更短的路：每张卡自己的 HBM 到自己的 SM，8 TB/s。生成一个 token 要把这一步用到的权重从 HBM 读一遍，读完就丢，下一步再读。L2 只有一百多 MB，放不下。

TP4 的意思是：同一个 token 同时在 4 张卡上走完全部 40 层，每张卡只拿每个矩阵的 1/4（或者整份复制），每层算完用 NVLink 对一下结果。所以上面的动画里，4 张卡上的 4 颗琥珀色小球始终在同一高度。

Engram 这张 n-gram 查找表 189 GiB（FP8），按行切到 4 张卡，每卡 47.5 GiB，比所有 attention 权重加起来还大几十倍；它每步只查几十行。把它挪到 Grace 内存（host table）每卡能多出约 47 GiB 给 KV，这轮实验没开。

01

CPU 这一侧：GPU 在算第 n 步时，CPU 已经在排第 n+1 步

6 个进程：主进程（HTTP + TokenizerManager）、4 个 Scheduler（每张卡一个）、1 个 Detokenizer。它们之间是单向的 ZMQ 管道。

只有 rank0 的 Scheduler 连 ZMQ。它每一轮都用 gloo 把收到的请求列表广播给另外 3 个 rank，没有请求时也广播一个长度 0。输出同样只由 rank0 发出，其余 3 个 rank 照样记账，但不往外发。已核实

默认循环是 event_loop_overlap：先把下一批的 GPU 工作 launch 出去，再阻塞等上一批的 token 拷回 CPU。整个循环里 CPU 只在 copy_done.synchronize() 这一处阻塞。

下一步的输入 token 不经过 CPU。采样结果写进 GPU 上的 FutureMap.output_tokens_buf，下一步在同一条 stream 上按 req_pool_idx gather 出来当 input_ids。已核实

overlap 的代价是结束判断晚一步：请求在第 n 步生成 EOS 时，第 n+1 步已经发出去了，所以每个请求最后都多跑一步，结果丢掉。

CUDA graph 里装的是整个 forwardembedding → 40 层 → lm_head → logits all-gather 都在图里；attention metadata 准备和采样在图外。bs1、bs128 都正好是捕获尺寸，不 padding。decode_cuda_graph_runner.py:1175-1226, 1440-1442 · cuda_graph_hook.py:642-675
4 张卡各自采样，不同步结果每张卡都拿到完整的 [bs, 129280] logits，各自 argmax（或用 rank0 广播的同一个 seed 采样）。代码注释说默认出于性能不在 rank 间同步 token id。layers/sampler.py:676-692 · tp_worker.py:370
一步只给每个请求分 1 个 KV 槽page_size 是 256，同时从 full 池和 SWA 池各拿一个槽；压缩 KV 和 index key 按同一张 page table 推算位置，不单独分配。ModelWorkerBatch 在 v0.5.21 里已经没有了：ScheduleBatch 直接变成 ForwardBatch。schedule_batch.py:3557-3611 · allocator/swa.py:419-454
客户端测到的 TPOT 是流水线周期只要 CPU 一轮比 GPU 一步短，token 间隔就等于 GPU 一步；Detokenizer、ZMQ、HTTP 只给每个 token 加一个固定延迟，不改变间隔。CPU 有没有暴露成 GPU 空隙，要 nsys 看相邻两次 replay 之间的空白。估算facts/runtime.md R6–R7

40 层地图：只有 4 层存长程 KV，只有 8 层自己挑 top-512

40 层每层都有自己的滑动窗口（最近 128 个 token）。长程的压缩 KV 只由第 2、8、14、20 层算和存，其余层读前面同压缩比的 source 层那一份。

挑 top-512 的 indexer 也只有 8 层：2/8/14/20 是 Full，对全部可见条目打分；24/28/32/36 是 Reindex，用自己的 q 给第 20 层的 key 打分，只看第 20 层发布的候选池。剩下 30 层直接复用前面最近一个 indexer 层选出来的 512 条。悬停或点击每一格看细节。

03

Attention：64 个头共用一行 512 维 KV

V4.1 的权重里只有一个 wkv（5120→512）。这 512 维同时当 K 和 V，64 个 query head 共用。

TP4 把 64 个头切成每卡 16 个（wq_b 列切，wo_a 每卡 2 组，wo_b 行切）。KV 没有 head 维度切不开，所以 wqkv_a、KV cache、压缩器和 indexer 的全部 32 个打分头都是每卡一整份。

bs ≤ 8 时，稀疏 attention 走专门为 16 个头写的 swapab kernel，把头数放在 MMA 的 N 维。bs 更大时走 FlashMLA，16 个真头补成 64 个，后 48 个是零。已核实

m=2 的层每两个 token 才凑出一条压缩 KV。凑不齐的那一步压缩器什么都不写，这个 token 暂时只能靠滑动窗口被看到。

04

mHC · Engram · MoE · 通信：attention 之外的路

残差不是一条，是 4 条。每个子层先把 4 条 [5120] 合成一个输入，算完再按一个 4×4 的混合矩阵写回 4 条。这就是 mHC。

V4.1 的调度是“系数用在下一个子层”：每个子层把 4 条拼成 20480 维，乘 [24×20480] 得到 24 个数（4 pre + 4 post + 16 comb），comb 用 20 轮 Sinkhorn 变成双随机矩阵。这件事在副 stream 上和 attention / MoE 并行做，一步 80 次。已核实

Engram 只在第 1、14 层，在 attention 之前：24 个 n-gram 哈希行号 → 查 188.8 GiB 的表（每卡 1/4 行）→ all-reduce 12 KiB → 投影 6144→25600 → 门控加回 4 条残差。

MoE：router 5120→384，sqrtsoftplus 打分，top-6，权重 ×1.5。每张卡存每个 expert 中间维的 1/4（576 列，补齐到 640），FP4 权重 × MXFP8 激活，kernel 是 trtllm_fp4_block_scale_routed_moe。shared expert 是 FP8，在另一条 stream 上跑。

每步 84 次 collective，全部是小消息1 次 embedding all-reduce + 80 次每层融合 all-reduce（每层 2 次）+ 2 次 Engram all-reduce + 1 次 logits all-gather。bs1 每次 10 KiB 左右，NVLink 上传输只要零点几微秒，时间都花在启动和同步上。facts/moe.md M5
all-reduce 是 SGLang 自己的 one-shot pushCustomAllReduceV2，CUDA graph 下 ≤2.25 MB 走它，不是 NCCL。bs ≤ 8 时一个 kernel 里做完 all-reduce + mHC post + 下一个子层的 pre 合并 + RMSNorm；MoE 那次还顺带做 finalize、加 shared expert、量化成 MXFP8。deepseek_v4.py:3562-3604, 3673-3703

05

3.20 ms 时间账：读字节只要 0.6 ms

bs1 时每张卡每步一共读约 4.5 GB。按 8 TB/s 的峰值，这只要约 0.57 ms，不到 3.20 ms 的五分之一。

剩下的时间不在“搬数据”上。84 次 collective，每次传的数据很少，耗时主要在启动和 4 卡之间的同步，按每次 5～20 µs 算是 0.4～1.7 ms。再剩下的约 2 ms，是 40 层里上千个小 kernel 一个接一个跑的串行延迟、多条 stream 之间的等待，以及图外的 attention metadata 准备。

这也解释了为什么 bs1 时把上下文从 16K 加到 128K，TPOT 只涨 1.7%：bs1 的瓶颈是延迟，不是带宽。下一步要用 nsys 把灰色那一段拆开。

06

bs 从 1 到 128：多出来的 9.5 ms 去哪了

请求数涨 128 倍，每个 token 的耗时只从 3.20 涨到 12.71 ms（4 倍），总吞吐涨了约 32 倍。

原因在 MoE。每个 token 选 6 个 expert，但 128 个 token 选的不一样，合起来会覆盖很多不同的 expert。只要有一个 token 选中，这个 expert 的权重就要整个从 HBM 读一遍。 按均匀路由，激活的 expert 数是

U(bs) = 384 × (1 − (1 − 6/384)bs)

bs1 是 6 个，bs128 约 333 个，bs512 基本全部 384 个。bs128 时每个 expert 平均只分到 2.3 个 token，FP4 GEMM 的计算密度约 9 FLOP/B，离 B200 的分界线（约 1250）差两个数量级，所以时间只看读了几个 expert。

铜色实线是 expert 权重读取的下限（按峰值 8 TB/s），紫色虚线是“bs1 实测 + 多读的 expert”。每个 expert 每层每卡 5.22 MB（TP4 把 2304 切成 576 列，FlashInfer 再补齐到 640）。bs128 时多读的 expert 约 8.5 ms，预测 11.7 ms，实测 12.71 ms：MoE 一项约占 9.5 ms 增量的 90% 估算。

右侧灰色区域：TP4 每张卡都要存全部请求的 KV，按启动日志估算约 135 个请求就放不下，所以“bs 超过 256 后 MoE 饱和、吞吐重新接近线性”这个预测只能在 DP4 上验证。

07

TP 还是 DP：同一个 token，换一种分工

V4.1 的 64 个 query head 共用一份 512 维 KV。TP 按 head 切，KV 却切不开，只能每张卡存一份完整的。

attention TP4：每卡 16 个 head，但每卡要存、要读全部请求的 KV，indexer 也在每张卡上对全部请求完整打一遍分。attention DP4：每卡一套完整的 attention 权重，只管 1/4 的请求，MoE 前把 4 卡的 token all-gather 到一起，MoE 仍然是 TP4。

实测两点都是 TP 快。bs1 时 DP 只有代价：每卡多读约 4.2 GiB attention 权重（≈0.57 ms），空 rank 也回放整张 graph，TP 路径上的 all-reduce + mHC 融合在 DP 下关掉。bs128、16K 时，DP 省下的 KV 读取（0.2～0.9 ms）和多读的权重基本抵消，剩下约 1.6 ms 推测来自实现差异 估算。

DP 的真正优势在容量：每 token 的 KV 只存一份，扣掉多存的权重，估计能放下的请求约是 TP 的 2.7 倍（≈360 对 ≈135）估算。
